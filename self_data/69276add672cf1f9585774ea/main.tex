\begin{abstract}
We target automatic, per-item inventory tracking in home kitchens from
first-person video. Given a participant's current inventory monitoring
list (known items with package size and reference images, but no
provided starting amount) and an untrimmed kitchen-activity video, the
system outputs which inventory items were used and how much remains,
under an objective of minimizing cloud model cost without sacrificing
amount accuracy. \sys addresses this cost--accuracy problem by
splitting the task across edge and cloud: lightweight edge observers
localize inventory interactions over the full video, while a cloud LLM
planner sends only selected before/after windows to a VLM reasoner.

\subsection{Task Definition and Benchmark Construction}
\label{sec:bg-task}

The input to the inventory-tracking task is a natural, untrimmed
egocentric recording of a cooking session and the household 
inventory monitoring list, which contains all monitored items 
that are not yet depleted. Each entry stores the item's identity, 
reference image, and package size.
We use \emph{amount} to mean the food-specific quantity that 
a household would naturally record: weight for fluids,
granular foods, sauces, and other bulk items, and count for 
discrete items such as eggs, fruit, or individually packaged units. Given the
video and monitoring list, the system must decide which items were used
and update each used item with its remaining amount from visual evidence. Section~\ref{sec:dataset}
provides the full collection protocol and item/household breakdowns.

\subsection{Related Work}
\label{sec:bg-related}
\paragraph{Long video understanding}
Egocentric long video understanding systems exploit hand-object interactions, repeated places, and persistent scene structure to
build affordance maps, active-object memories, and scene
memories for later retrieval and reasoning~\cite{golettoAMEGOActiveMemory2024,nagarajan2020ego,price2022unweavenet,rodin2024action,fanEmbodiedVideoAgentPersistent2025, huang2025building,ramakrishnan2023naq,nagarajan2023egoenv}. However, they do not support revisiting visual evidence to understand fine-grained object states such as food quantity.
Recent agentic video understanding systems address long-context limits
by compressing video into memories, retrieving candidate evidence
spans, and using LLM/VLM agents to decide what to inspect
next~\cite{fanVideoAgentMemoryAugmentedMultimodal2025,wang2025active,
yan2025ava,zhang2025deep,rege2026agentic, shen2026vgent,zhou2026reagent,zuo2026videolucy}. Their optimization target is 
accuracy under the VLM context-window bottleneck: the agent retrieves
or selects evidence so the model need not ingest the full video at
once. When these systems report efficiency, they usually measure
retrieved frames, input-token reduction, or inference time, rather than
the priced cloud cost of a recurring deployment.
\sys adapts the agentic pattern to a resource-constrained
inventory-monitoring task: lightweight edge observers localize
candidate item-use events, and a cloud planner reserves VLM reasoning
for the selected moments that reveal food amount.

\paragraph{Object state-change understanding}
 Existing benchmarks and methods ask VLMs or video models
to identify symbolic states such as open/closed or on/off, infer
multi-label food states such as cracked or whisked, predict how several
objects' states evolve through procedural actions, or track an object
through a visible transformation~\cite{ukai2025status,
tateno2025learning,zameni2025moscato,sunTrackingUnderstandingObject2025}.
These tasks demonstrate that object state is temporally grounded and
often depends on action history. However, they typically operate on
image pairs, narrated or action-segmented procedural videos, or tracked
object tubelets in which the relevant object interaction is already in
view. Our setting instead starts from long untrimmed household video and
an inventory list of known items. The system must retrieve the few
visual moments that can update each inventory-list entry, estimate a
quantitative remaining amount in weight or count, and do so under a
cloud VLM token budget.

\paragraph{Egocentric video benchmarks}
Egocentric video benchmarks provide the closest dataset context for our
task, but their annotation targets differ from ours. They
provide action segments, hand-object masks and relations, narrations,
recipe steps, ingredients, object motion, VQA labels, and
procedure-error labels~\cite{damenRescalingEgocentricVision2022,
darkhalilEPICKITCHENSVISORBenchmark2022,grauman2022ego4d,
perrettHDEPICHighlyDetailedEgocentric2025,
peddiCaptainCook4DDatasetUnderstanding2024,plizzari2024outlook,grauman2024ego,wang2023holoassist,jia2022egotaskqa,huh2025epic,zhu2023egoobjects,huang2024egoexolearn,chen2026egoplan}. These labels do not evaluate systems' capability to
recover the remaining quantity of a food package. Our benchmark therefore targets a different state
variable: package-level food amount, measured by weight or count, for
known inventory items across natural cooking sessions.

Together, these lines of work leave a systems question open. Fine-grained
food amount estimation requires VLM-level visual reasoning, but daily
inventory monitoring repeats that reasoning across sessions and items
under a cloud-inference budget.

\section{Motivation Study}
\label{sec:bg-motivation}

We begin with whole-video VLM inference because it directly applies the visual reasoning
capability that remaining-amount estimation requires. This
baseline isolates the bottleneck that motivates \sys: package-amount
evidence requires a capable VLM, yet most frames in a cooking session
are irrelevant to that evidence.
Throughout this section we ground each claim in a pilot study: 10~wild
egocentric cooking sessions ($\approx$2.2~hours at 1~fps, 7{,}977
sampled frames, 64~human-annotated usage events) drawn from our dataset
(\S\ref{sec:dataset}).

\paragraph{Whole-video VLM inference is expensive.}
As a whole-video baseline, we send every sampled frame in a session to
Gemini~3.1~Pro and ask the model to infer the final inventory state
end-to-end. On this pilot, the baseline
costs \$8.05 at current paid-tier rates~\cite{googleGeminiAPIPricing2026}
--- \$3.66 per hour of recording, or over \$100/household/month at one
hour of daily logging. The cost driver is the linear scaling of input
tokens with video length~\cite{openaiAPIPricing2026,googleGeminiAPIPricing2026}.
This finding rules out treating long-horizon egocentric video as a
stream that can be routinely handed to a cloud VLM end-to-end.

\paragraph{Whole-video context buries amount evidence.}
The same baseline also provides a diagnostic for context distraction
before amount reading: most frames are not quantity evidence. When a VLM receives a
long egocentric session, the
answer-bearing views are embedded among hundreds of visually redundant
or misleading frames: idle cooking, off-target object handling, hand
occlusions, motion blur, and views of food after it has left the
queried package, which no longer reveal the package's remaining amount. On the
pilot, Gemini~3.1~Pro detects only 53 of 64 usage events (82.8\%)
when the whole video is placed in context; restricting the context to
human-annotated inventory-interaction frames recovers 58 of 64
(90.6\%). This diagnostic suggests that selection is not only a cost
mechanism: long context can distract the VLM from the sparse views
needed for a numeric inventory update.

\paragraph{Inventory-use evidence is sparse.}
The design opportunity is that the moments needed to estimate
an item's remaining amount are sparse but localizable. For each
inventory item, the system must first detect whether an item-use event
occurred and then find post-event views that reveal the package's
remaining state. The short action in which food leaves the package or
container is a \emph{portion-transfer moment}: pouring, scooping,
cutting, removing, or discarding food. In a mining pass over
HD-EPIC annotations,
interactions with inventory-like source items account for only roughly
$6$\% of total cooking-video duration.\footnote{We count a segment as
inventory-like when the annotated noun corresponds to a source item or
package whose household stock could change through retrieval,
dispensing, removal, or put-back. We exclude downstream cooking actions
on already transferred food, such as stirring, frying, or mixing
ingredients in cookware.} The rest of the timeline includes
meal preparation around non-query items, cooking, waiting, washing
dishes, and other activity not directly changing inventory
state~\cite{perrettHDEPICHighlyDetailedEgocentric2025}. This
sparsity is the insight behind \sys's locate-then-read split:
lightweight CV signals can pre-select candidate item-use events, so
an expensive VLM is invoked only where it can observe the before/after
evidence needed for an inventory update.

\section{System Design}
\label{sec:system}

\sys separates locating from reading. As shown in
Fig.~\ref{fig:system-overview}, the edge endpoint receives an untrimmed
session and the current inventory monitoring list, then converts them
into compact item-interaction timelines. The cloud planner uses those
timelines to choose which video frames to fetch for the VLM reasoner and
which unresolved items to revisit. This split keeps full-session search
on lightweight edge observers and reserves VLM calls for the hard visual
reading step: estimating starting amount, transferred amount, or
remaining amount from selected evidence.

\subsection{Inputs and assumptions}
\label{sec:system-inputs}

We assume that each item is registered when it enters the household and
remains in the inventory monitoring list until marked depleted. This
narrows the problem to tracking state changes of \textit{known
inventory items}, avoiding the separate challenge of open-set instance
retrieval over large food catalogs. Given the untrimmed video and
current inventory-list snapshot, \sys assumes no manual segment
labels, scripted recipe structure, or known order of item use.
Registration also stores package size, reference image, measurement
unit, and a package-transparency tag inferred from the product name and its
image: transparent if the package is likely to expose its contents, and
opaque otherwise.

\subsection{Edge timeline construction}

The edge stage does not try to estimate amount. Its role is to construct
a query-set-aware intermediate representation: an item-interaction
timeline that records when each monitored item may have changed state,
which routine context surrounded the interaction, and how confidently
the contact matched the registered inventory. Figure~\ref{fig:edge-observer}
shows this conversion from raw frames and a registered item list to
a text timeline. In the example, noisy per-frame detections for eggs and
tomatoes are merged into one stove segment with per-item peak-DINO times
and active spans.

\begin{figure*}[t]
  \centering
  \includegraphics[width=0.92\textwidth]{Figures/lightweight_observer.pdf}
  \Description{Edge observer pipeline: 1 fps sampled frames pass through
  hand-object interaction detection, inventory-item matching, scene
  tagging, and temporal grouping to form item-interaction timelines.}
  \caption{Lightweight edge observer pipeline.}
  \label{fig:edge-observer}
\end{figure*}

\paragraph{Sampling for edge-feasible localization.} The household edge
endpoint samples the video once at 1~fps and runs frame-based detectors
on those images. This second-scale sampling captures ordinary kitchen
manipulations while avoiding the GPU memory and processing cost of
running clip-level video models over the full session
\cite{liu2024end, zhang2022actionformer,li2024videomamba,wang2024internvideo2,zhang2025videollama}.

\paragraph{Localizing moments of physical contact.} Inventory state
cannot change without physical contact, so contact is the first
selection predicate. Hands23~\cite{chengRicher2DUnderstanding} filters
the 1~fps stream to frames where a hand is in \emph{object-contact} and
returns the interacted-object box. This box, illustrated as the masked
crop in Fig.~\ref{fig:edge-observer}, is the visual evidence passed to
item matching.

\paragraph{Matching contact to inventory.} Contact alone is not enough:
the system must bind each possible state change to the household's
current inventory list. For every retained frame, the edge endpoint
matches the in-contact crop to the registered item images
(Section~\ref{sec:system-inputs}) using
DINOv3~\cite{simeoni2025dinov3} embeddings. This makes localization
query-set aware. In Fig.~\ref{fig:edge-observer}, the crop is scored
against the active list entries, so the downstream timeline records
``Eggs'' and ``Tomatoes'' rather than open-vocabulary object labels.

\paragraph{Adding routine context with scene tags.}
The same item can appear during retrieval, preparation, transfer, or
put-back, but these stages differ in whether they reveal amount. \sys
runs OWLv2~\cite{minderer2023scaling} on inventory-relevant contact
frames with prompts for common kitchen scene tags: storage, sink, and
stove. Each frame is assigned the tag whose prompt receives the highest
detector score, or left untagged when no prompt matches confidently.
Together with temporal order, the scene tag helps the planner separate
storage retrieval, sink preparation, cooking, and put-back stages
\cite{golettoAMEGOActiveMemory2024,huang2025building,nagarajan2020ego}.
The transparency tag from item registration is used later in the same
way: transparent packages make storage or put-back views plausible
fill-level evidence, while opaque packages direct the planner to access
or use windows that show the open package interior, post-use contents, or
dispensed amount.

\paragraph{The item-interaction timeline abstraction.}
Temporal merging turns per-frame observations into the compact
representation consumed by the planner. A frame contributes to an item's
timeline only when Hands23 reports object contact and DINOv3 matches the
contacted crop to that item's registration image above a confidence
threshold. The endpoint bridges short gaps, removes isolated matches,
and merges nearby matches for the same item or for multiple items
handled in the same short interval. Each segment records the fields shown
in Fig.~\ref{fig:edge-observer}: start and end time, dominant scene tag,
active inventory items, strongest DINOv3 timestamp for each item, and
the interval over which each item was visible during contact. The
timeline is therefore not just a detector output; it is the edge-side
state-change hypothesis that the cloud planner turns into amount
observations.


\subsection{Cloud evidence planning}
The cloud stage solves the second selection problem: deciding which
localized interactions are worth observing with a VLM. Its design
follows from a gap between interaction localization and amount evidence:
the edge timeline can identify when an inventory item is likely active,
but it cannot know which frames reveal usage and post-use package state.
Figure~\ref{fig:cloud-agentic-plan} follows one example: a first planner
round resolves eggs, leaves tomatoes unresolved, then revisits a likely
tomato-bag view in the next round.

\paragraph{Interaction segments are not evidence windows.}
For a given item, the edge output is a sequence of short contact
segments, typically 5--15~s each. The ordered segments show how use
unfolded--retrieval from storage, opening or unpacking, portion transfer,
views of food after it leaves the package, and put-back or final
visibility--but the answer-bearing evidence usually lies in only part of
that sequence. In Fig.~\ref{fig:cloud-agentic-plan}, tomatoes appear at
the counter, on the cutting board, and in the pan; the latter views help
verify use, but the bag view is more likely to expose remaining amount.
Thus an interaction segment may be visually rich while containing only a
few answer-bearing frames.

%699s out of 3653s overlap with evidence
In our pilot videos, the edge pipeline retains 46\% of sampled frames
from the full videos, but only 19.5\% of those edge-retained frames
contain direct remaining-state evidence.
This mismatch
motivates a cloud stage that selects observation windows around
inventory evidence rather than reading every frame retained by the edge
pipeline.

\paragraph{Seeking amount windows from item-interaction timelines.}
The planner operationalizes the amount-evidence model by mapping each
item-interaction timeline onto candidate pre-use, transfer, and post-use
windows under a fixed frame budget. It reads the timeline fields shown in
Fig.~\ref{fig:edge-observer}--segment times, scene tags, co-handled
items, active spans, and peak-DINO timestamps--plus the per-item
transparency tag stored at registration. It then uses temporal order and
package transparency to infer likely retrieval, access,
portion-transfer, and final-visibility stages.

\emph{Stage-sampling} windows give sparse coverage: for each active item
in each segment, the planner selects a 1~s window centered on that
item's peak-DINO timestamp.
\emph{Transfer-inspection} windows allocate longer 3--10~s intervals
around likely opening or portion-transfer moments. These windows cover
frames where the package opens, food leaves the package, and the package
interior, dispensed portion, or post-use contents become visible. The
longer window handles viewing-angle, hand, and utensil occlusion around
the package opening or container interior.
For transparent packages, put-back or final-shelf views expose the
remaining fill level, so the planner targets a long window there.
For opaque packages, closed final-shelf views hide contents; the planner
instead brackets opening and dispensing, where the package interior or
dispensed amount is visible.
Each window can name multiple target item ids when the same frames cover
multiple target items.

\paragraph{VLM reasoner.}
The VLM is reserved for reading amount from the selected visual evidence,
not for searching the full video. Selected stage-sampling and
transfer-inspection windows are flattened into a chronological
multi-image prompt with the candidate item list and the image-to-segment
mapping. For each candidate item, the reasoner first decides whether the
item was used. It then fills an amount state with three independent
visual readings when frame evidence supports them: starting amount before
use, amount used during transfer, and remaining amount after use. A
reading remains empty when no supporting frame is present; the reasoner
does not infer one reading from the others.

The reasoner also summarizes every selected segment. Each segment observation
describes the visible action, such as accessing, opening, dispensing, views of
food after it leaves the package, restocking, or idle frames, and whether the
segment provides pre-, during-, or post-use evidence for the candidate item.
These observations are carried forward as annotations on the retained timeline,
so the next planner sees what the VLM actually inspected and which amount
evidence remains missing.

\paragraph{Replan.}
\sys treats missing amount evidence as a bounded recovery problem. The
first observation plan is intentionally small, so it can fail in a
specific way: it may select a non-diagnostic window that confirms use
without showing the package-state evidence needed for the remaining
amount. For example, tomatoes on a cutting board or in a pan show that
the bag was used, but not the bag's starting or remaining amount.
Replanning turns this partial VLM
observation into feedback. The next plan is conditioned not only on the
edge timeline, but also on which amount readings remain unobserved after
the previous VLM call. After each round, an item is resolved if the
reasoner directly reports a remaining amount, or if both the starting
amount and amount used are grounded so the remaining amount can be
derived downstream. Items that have neither a direct remaining amount nor
two grounded readings remain unresolved.

Before the next planner call, \sys filters the context to the
unresolved items.
For each unresolved item, the planner receives the retained timeline,
the current and missing amount readings, and the segment observations
produced by the VLM reasoner so far. It then emits another bounded set
of observation windows for missing evidence, such as a post-use package
view or a longer segment around the likely portion-transfer moment. In
Fig.~\ref{fig:cloud-agentic-plan}, the first round leaves tomatoes
unresolved, so the next plan revisits the earlier tomato-bag observation
with a longer window.

New VLM outputs fill only missing readings; previously grounded readings
are preserved.
The loop stops when every candidate item has a grounded update or when the
fixed round budget is exhausted. In evaluation, varying this round budget
exposes the cost--accuracy trade-off.

\subsection{Budget control}
\label{sec:budget-control}

In the case when a user's deployment of \sys is constrained by a cloud budget, \sys adapts to a tighter budget by shrinking the set of items it monitors each session: rather than measuring every detected item, it skips items it judges unlikely to be approaching depletion and concentrates the available observer calls on those that are.

The principle is that an item is only worth re-measuring when its remaining amount is plausibly close to running out. \sys maintains a lightweight running estimate of each tracked item's remaining stock, seeded at the receipt capacity when the item enters the inventory and overwritten by every observer measurement. Between observations, the estimate decays by a per-item prior on typical per-session consumption. As long as this estimate stays comfortably above half the receipt capacity, the observer is suppressed and the item is dropped from that session's observer prompt. Once the estimate would cross the 50\,\% mark, the next session forces a fresh measurement; if the measured amount likewise lies at or below half, the system raises a low-stock alarm to the user. A small safety cap forces a refresh after a configurable number of consecutive skips on the same item, which keeps the simple decay model from drifting unboundedly far from reality.

This design intentionally exposes two knobs. The 50\,\% threshold is the primary lever a user adjusts when their budget changes: pushing it lower trades alarm lead-time for fewer observer calls, while still guaranteeing that an alarm precedes depletion as long as the per-item prior is approximately correct. The refresh cap acts as a sanity floor against bad priors, ensuring that even an item the controller persistently underestimates gets re-measured periodically. Because every alarm is gated by an observer call, a spurious alarm on a non-depleting item costs at most one extra observation, already counted toward the budget; there is no separate false-alarm penalty.

\subsection{Benchmark protocol}

Each evaluation unit pairs an untrimmed egocentric session with the
participant's pre-session inventory snapshot: monitored in-stock items,
their names, package sizes, and reference images, but no starting
amount. Given this video--snapshot pair, a method predicts which
items were used and each used item's remaining amount. 

\paragraph{Implementation.}
All experiment cells use fixed prompts, parsing
schemas, model choices, and no per-session prompt tuning. The default
\sys stack uses a GPT-5.4 text planner over edge-produced
item-interaction timelines and a Gemini-3.1 Pro reasoner over selected
video frames. The planner returns bounded observation windows for
sparse stage sampling, likely transfer inspection, and final
visibility; the reasoner returns structured per-item state updates.
The reported \sys row uses fixed frame budgets and a three-round
plan--observe cap for every session; ablations change only the
indicated cue or round limit. The code artifact includes the full
prompts, command lines, decoding settings, parser, and
example per-session JSON logs.

For the whole-video baseline, we convert all source clips to $1$~fps and split the concatenated video into chunks of at most
$20$~minutes. Each chunk receives the full in-stock inventory list and
the same amount-reading schema as the \sys reasoner. The final
session-level prediction aggregates the chunk outputs: an item update
is carried forward until a later chunk reports the same item, at which
point the later reading replaces the earlier one. The $20$-minute cap
is set empirically to avoid exceeding Gemini 3.1 Pro's max output tokens limit under high thinking level.


\subsubsection{Metrics}

\paragraph{Inventory-update performance.}
Tables~\ref{tab:primary}, \ref{tab:ablation-deltas},
\ref{tab:household-generalization}, and \ref{tab:vlm-switch} report
amount-aware inventory F1, amount-update coverage,
hallucinated-update rate, and projected monthly cloud cost. Conditional
amount error is reported separately in the amount-reading breakdowns.

\paragraph{Amount-update coverage and hallucinated updates.}
Let $G$ be the set of ground-truth item-use events, $M \subseteq G$ be
the matched used-item events, $M_{\mathrm{amt}} \subseteq M$ be the
matched events for which the system returns a numeric session-end
remaining-amount estimate, $U=G\setminus M$, and $H$ be hallucinated
used-item predictions. Amount-update coverage is $|M_{\mathrm{amt}}|/|G|$: a
detected use that lacks a numeric remaining-amount estimate does not
update the inventory state and is not credited. A hallucinated update is
a predicted used-item record that
cannot be matched to any ground-truth item-use event in the session. We
report hallucinated-update rate as $|H|/(|G|+|H|)$, equivalently
$|H|/(|M|+|U|+|H|)$. This workload-normalized diagnostic measures how
much the inventory-update stream is polluted by extra predicted updates
in a setting with no meaningful true negatives. Items skipped by the
planner, missed by the edge pipeline, or returned as unresolved count as
misses for coverage.

\paragraph{CNPE}
\label{sec:cnpe}
For matched items with numeric remaining-amount estimates,
capacity-normalized percentage error is
$\mathrm{CNPE}_i=\lvert \mathrm{pred}_i-\mathrm{GT}_i\rvert C_i^{-1}
\times 100$, where $C_i$ is item $i$'s package capacity. We report CNPE
on remaining amount unless stated otherwise. Because CNPE conditions on
a numeric prediction and does not penalize missed or hallucinated
updates, we use it as a diagnostic for VLM amount reading rather than
as the end-to-end inventory metric.

\paragraph{Amount-aware inventory F1.}
Let $\mathcal{P}$ be the predicted-used item records. For each
$g \in G$, let $e_g$ be its remaining-amount CNPE if matched to a
numeric prediction, and set $q_g=1-\min(e_g,100)/100$; unmatched events
or matched events without a numeric amount estimate have $q_g=0$. With
$Q=\sum_{g \in G}q_g$,
$R_{\mathrm{amt}}=Q/|G|$ and
$P_{\mathrm{amt}}=Q/|\mathcal{P}|$. Inventory F1 is their harmonic
mean, reported as a percentage.
Hallucinated predictions lower precision; if no item is predicted,
$P_{\mathrm{amt}}$ and $F1_{\mathrm{inv}}$ are zero. Thus the precision
term is amount-aware; the hallucinated-update rate above remains a
separate diagnostic.

edge-stage throughput separately from amount accuracy, treating $1$~fps
as the sampled-video workload rather than a hard real-time requirement.

\paragraph{Analysis.}
Figure~\ref{fig:runtime} compares server-side logs from the common timed

than the recorded video duration: the recorded end-to-end pass stays

The three edge stages run sequentially on a single GPU, so the edge
memory budget is set by the largest single stage rather than their
sum. Measured on an NVIDIA RTX 6000 Ada, peak allocations are
$0.84$~GB for Hands23, $17.08$~GB for DINOv3 ViT-7B (bfloat16), and

Jetson trace in Figure~\ref{fig:runtime} uses a smaller DINOv3
ViT-L/16 backbone, illustrating the main edge-memory tradeoff for
VRAM-limited deployments.

\section{Conclusion}
\sys\ shows that long-horizon inventory tracking need not spend cloud
VLM reasoning in proportion to video duration. By locating candidate
item interactions on the edge and letting a text planner choose the
windows that contain amount evidence, the system preserves inventory-update
quality relative to whole-video VLM inference while using
$10.2\times$ fewer input tokens and incurring $5.2\times$ lower
projected monthly cloud cost on the annotated in-the-wild cohort. The remaining
cost depends on the density of monitored item interactions: sparse
sessions yield the largest savings, while dense sessions leave less
irrelevant video to discard. The same cost--quality tradeoff appears
in the per-household results and in the Gemini Pro/Flash sensitivity
study. The amount-reading breakdowns show why this
architecture is viable: the evaluated VLMs can estimate remaining food amount
coarsely once given relevant evidence, but fluids, opaque packages, and
near-empty containers remain the hardest cases. Together, the results support
edge--cloud orchestration as a practical path for wearable memory
systems that need fine-grained state updates without streaming every
frame to a cloud VLM.
